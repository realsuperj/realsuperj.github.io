# 去重仲裁

第 3 步用。这是整个流程里**最容易造成不可逆损失**的一步——判错了就会误删用户的独立 skill。

## 为什么必须单独一轮

第 2 步是分批做的，每批只看得见自己那十几条。这会同时产生两类错误，而且分批时无法自查：

- **过度合并**：批内几条主题相近，就被打上同一个去重键。若这批恰好是同一主题的多个不同作者作品，会被整批误判为重复
- **漏合并**：同一个 skill 的 v1 和 v3 落在不同批次，各自拿到不同的键，重复没被发现

所以第 3 步必须拿到**全部条目**重新过一遍，不能与第 2 步合并，也不能只复核第 2 步标记为重复的那些。

## 核心判据

> 只有「同一 skill 的不同版本」「同一份内容的不同导出格式」才算重复。**不同作者、不同方法论框架的同主题 skill，即使目标人群完全一样，也必须各自保留。**

### 算重复

| 情形 | 例子 |
| --- | --- |
| 同一 skill 的不同版本 | `xx教练_v1` 与 `xx教练_v3`，正文结构与术语体系一致，后者是前者的扩充 |
| 同一内容的不同导出格式 | 同一份内容分别存成 `.md`、`.docx`、`.pdf` |
| 完整版与节选版 | 「xx完整版」与「xx」，后者是前者的前半部分 |
| 内容哈希完全相同 | 同一文件被下载了两次，文件名不同 |

### 不算重复

| 情形 | 为什么保留 |
| --- | --- |
| 同主题不同作者 | 方法论框架不同，价值互补 |
| 同主题不同切入角度 | 例如同为职业规划，一个从能力盘点切入、一个从市场需求切入 |
| 同一作者的不同 skill | 例如「简历改写」与「面试模拟」同属一个系列但功能不同 |
| 名称相近但内容不同 | 名称相似度高不等于内容重复，**必须看正文** |

最后一条是重灾区。名称里都含「职业」「教练」「战略」这类高频词的条目会大量出现，仅凭名称判断必然出错。

## 判断步骤

对每一组候选重复项：

1. 比对内容哈希。完全相同 → 直接判重复副本，不必细看
2. 哈希不同时，比对**正文结构**：章节标题序列、核心术语、流程步骤数。结构高度一致才继续
3. 结构一致时，比对**方法论框架**：是不是同一套模型、同一组概念。是则判为同一 skill 的不同版本
4. 以上任一环节不满足 → 判为独立 skill，各自保留

**默认倾向保留。** 拿不准时保留两者，并在报告里标注「疑似相关，请人工确认」。误删的代价远大于多留一条。

## 保留哪一个

判为重复后，保留规则按优先级：

1. 评分更高的
2. 分数相同时，内容更完整的（字数、章节数）
3. 仍相同时，格式更可用的（md > docx > pdf）

未保留的**移入 `99-重复版本归档`，不删除**。报告里标注它与哪一条重复。

增量模式下若新条目与存量条目重复且新版评分更高，**问用户是替换还是并存**，不擅自替换已有编号。

## 仲裁子代理提示词模板

能派生子代理时用这份模板，把全部条目的摘要一次性给它。不能派生时，你自己按这份要求走一遍。

```
你是去重仲裁员。下面是一批 skill 条目的摘要，每条包含：编号、名称、原始文件名、
内容哈希、字数、章节标题序列、核心术语、一句话摘要、第 2 步分批时打的初步去重键。

任务：重新判定哪些条目互为重复，产出最终去重键。

判据（严格遵守）：
- 只有「同一 skill 的不同版本」「同一份内容的不同导出格式」「完整版与节选版」算重复
- 不同作者、不同方法论框架的同主题 skill 必须各自保留，哪怕目标人群完全一样
- 名称相似不等于内容重复，必须看章节结构与核心术语
- 拿不准时保留两者，标注「疑似相关」

注意：初步去重键是分批打的，很可能有错，两类错误都要修：
- 过度合并：一个键下挂了很多条，检查它们是否真是同一 skill
- 漏合并：同一 skill 的不同版本散落在不同键下

输出 JSON：
{
  "groups": [
    {
      "final_key": "唯一键",
      "members": ["编号1", "编号2"],
      "keep": "编号1",
      "reason": "判定依据，必须指出具体的结构或术语一致点",
      "confidence": "high|low"
    }
  ],
  "singletons": ["未与任何条目重复的编号"],
  "suspected": [
    {"members": ["编号3","编号4"], "note": "疑似相关但不判重复的理由"}
  ]
}

每一组的 reason 必须写出具体依据，禁止「内容相似」这类空话。
```

## 仲裁结果的落地

- 账本里存**仲裁后的最终去重键**，不要存第 2 步的初步键——那正是出错的那个，存进去会让下次交叉查重继承同一套错误
- `confidence` 为 low 的组，在 dry-run 里单独列出提醒用户重点看
- 仲裁推翻了多少条初步判断，在报告的变更摘要里说一句，让用户知道这一步确实起了作用
