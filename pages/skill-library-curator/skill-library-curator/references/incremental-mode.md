# 增量模式

`{target}` 根下存在账本时走这里。目标是**只处理新增部分，不推倒重来**。

本模式尚未经过大规模实战检验，第一次对某个目录跑增量时**强制 dry-run**，人工确认移动计划后再执行。

## 账本格式

文件名 `Skill分析报告-数据.json`，与报告成对放在 `{target}` 根下。用可见文件名，因为隐藏文件在访达里看不见，也容易被同步工具丢掉。

```json
{
  "version": 1,
  "curated_at": "2026-08-30T21:00:00+08:00",
  "report_filename": "Skill分析报告.md",
  "model": "评分所用模型标识",
  "weights": {"完整度": 30, "结构化": 25, "实用度": 25, "原创性": 10, "交付物": 10},
  "taxonomy": ["01-职业发展", "02-个人成长", "..."],
  "entries": [
    {
      "no": "01-01",
      "path": "01-职业发展/01-01_双轨制职业战略教练",
      "original_name": "双轨制职业战略教练_分享版.zip",
      "hash": "内容指纹",
      "type": "skill",
      "score": 98,
      "grade": "S",
      "category": "01-职业发展",
      "dedup_key": "仲裁后的最终键",
      "user_override": null
    }
  ]
}
```

几个字段的用意：

- `path` **一律存相对 `{target}` 的路径**。用户随时可能给目录改名，存绝对路径会让账本整体失效
- `dedup_key` 存**仲裁后**的最终键。分批产出的初步键是出过错的那个，存进去会让下次交叉查重继承同一套错误
- `weights` 与 `model` 用于增量时校验口径是否一致，见下
- `user_override` 记录用户的人工调整（比如把某条从参考素材提回主清单），下次不再重复询问
- `report_filename` 记录报告实际叫什么，否则用户自定义过名字后，第二次运行会再生成一份默认名的

## 账本丢失时的兜底

从旧报告的「原始文件名」列反向重建。**按内容特征识别旧报告**——目录下存在含「原始文件名」列的 markdown 表格，即视为旧报告，不要按固定文件名去找。早期版本可能叫 `README.md`，用户也可能改过名，认死文件名会把已整理目录误判为首次整理而推倒重来。

重建出的账本缺少内容哈希，需要重新计算一遍；评分和分类可以从报告表格里读回来。

## 开工先校验口径

对比账本里的 `weights` 与 `model` 和本次的实际情况：

- 权重不一致 → 停下来问用户。要么沿用账本权重，要么改权重并触发**全量重评**。不允许两套权重的分数混在同一张按分数排序的表里
- 模型不一致 → 提示「打分尺度可能与存量不可比，建议全量重评或接受偏差」，由用户决定

## 扫描后分四类

对 `{target}` 的顶层条目（跳过已有分类目录、`.` 开头的条目、账本与报告自身）逐一对账：

| 情况 | 处理 |
| --- | --- |
| 已入账且哈希未变 | 跳过，完全不重新分析 |
| 已入账但哈希变了 | 用户就地更新了它，重新评分，**编号保持不变** |
| 扫到但不在账本里 | 本次新增，进完整分析流程 |
| 账本有但磁盘上找不到 | 用户自己删了或移走了，从账本剔除，报告里标注一句 |

## 为什么用哈希而不是修改时间

这条写下来是为了防止后来者「优化」成时间戳比对：

- skill 多为下载或转存所得，mtime 通常是**对方打包时的原始时间**而非获取时间，可能早于上次整理时间，导致漏检。解压产物继承 zip 内记录的时间，同理
- 同步工具、备份恢复、`cp` 复制都会把 mtime 刷成当前时间，导致整批误判为新增而重新分析
- 同一次整理内部就可能产生两种 mtime：移动的文件保留原时间，解压出来的内容是解压时间
- 哈希能识别「内容完全相同的副本」，时间戳做不到

哈希计算成本极低，数百个文件秒级完成。账本里的 `curated_at` 只用于在报告里展示「上次整理于何时」，**不参与增量判定**。

## 收纳夹要拆开

用户往往会新建 `00-待整理`、`待整理`、`inbox` 这类目录来放新收的东西。这是收纳夹，里面每个子项才是条目。但某个 skill 本身也可能就是个文件夹，所以判据按优先级：

1. 目录内直接含 `SKILL.md` → 它自己就是一个 skill 条目
2. 目录名命中收纳夹词表（待整理、新增、未分类、待处理、inbox、new、temp）→ 收纳夹，拆开逐个处理
3. 目录内有两个以上互不相关的顶层子项且无 `SKILL.md` → 疑似收纳夹，**列出内容问用户**，不自行决定

拆开后收纳夹本身若已空，删掉；若还有未处理的残留，保留并在报告里说明。

## 编号只增不重排

新条目并入某分类时，编号接该分类现有最大号往后排。**已有条目的编号一律不动。**

编号是身份标识，不是排序位。用户可能已经按编号记住了某个 skill，或者在别处引用过，重排会让他之前的记录全部作废。

代价是编号不再严格等于分数降序。解决办法是报告表格按分数排序展示，编号只作 ID 列，两者解耦。

## 新条目必须与存量交叉查重

新收的往往正是已有 skill 的更新版本，这一步不能省：

- **哈希完全相同** → 直接判为重复副本，归入 `99-重复版本归档`，不重新评分
- **主题查重** → 新条目的去重键与账本中存量条目比对，命中则进入仲裁。若新版评分更高，**问用户是替换还是并存**，不擅自替换已有编号

## 非 skill 文件同样要挑出来

收纳夹里常混入设计稿、方案文档、笔记、作业展示。这些走三态分流判为参考素材，进 `98-` 用 `M-` 编号，不占 skill 编号也不参与排序。判据见 `scoring-and-taxonomy.md`。

## 收尾

- 报告整体由账本重新渲染，渲染前把旧报告备份为 `Skill分析报告-上一版.md`
- 新报告开头加一句变更摘要：新增几条、更新几条、移除几条
- 整理完成后主动问一次是否要给目录改名（比如从「xx待整理」改成「xx」）
