# Skill 收藏整理器

把一堆来路不明、格式各异的 skill 收藏，整理成**分好类、编好号、评过分、去过重**的一份清单，并留下账本，下次只处理新增的。

## 路径约定

`{skillDir}` 表示本 SKILL.md 所在目录。你在读这个文件，所以这个绝对路径是已知的，用它拼出脚本路径，例如 `{skillDir}/scripts/extract_all.py`。解析不出来就直接问用户，**不要全盘 find**。

`{target}` 表示用户指定的待整理目录，每次运行由用户给出，任何地方都不许硬编码。

## 只整理评分，不负责安装

- **不安装 skill**。报告里有编号、名称、路径，用户说「装 01-04」时你读报告就能定位，不需要本 skill 额外提供功能
- **不批量按分数安装**。评分衡量「做得好不好」，不是「用户用不用得上」；且每个装上的 skill 都占用系统提示词空间、增加误触发
- **不改写 skill 内容**。只做移动、重命名、扩展名规范化，不动任何文件内部的字

## 第零步：开工前四件事

一件都不能跳。

### 1. 确认目标目录并回显

用户可以直接说路径、把文件夹拖进对话、或者没说（**则询问，不要猜**）。确认后回显：目录路径、顶层条目数、格式分布、工具探测结果，让用户确认是不是这个目录。

**作用域严格等于用户给的那个目录**：

- 只扫一层顶层条目，不向上遍历父目录，不主动发现同级目录
- 不递归进已识别为 skill 的文件夹内部去拆分它的子文件，文件夹内部只在提取文本时读取
- 跳过 `.` 开头的条目，显式排除账本与报告自身
- 已有的分类目录（形如 `01-` 到 `09-`、`98-`、`99-`）整体跳过，内容已在账本里

**如果用户指定的是某个已整理目录的子目录**（父目录下存在账本），停下来问：结果是并入父目录的分类体系并更新父账本，还是就在这个子目录内独立成一套？两种都合理，别替用户决定。

### 2. 判断首次还是增量

`{target}` 根下有账本 → 增量模式，读 `references/incremental-mode.md`。没有 → 首次整理，告诉用户全量分析耗时较长，并给出条目数作为预期。

账本丢失时从旧报告反向重建，**按内容特征识别旧报告**（存在含「原始文件名」列的表格即视为旧报告），不认文件名——用户可能改过名或用的是早期版本的命名。

### 3. 能力自检

实际跑一条无害命令看结果，**不要凭对自己身份的认知去猜**；不确定就问用户。

1. 能否执行 shell 命令
2. 能否运行 Python 并 import 所需依赖
3. 能否读写 `{target}`
4. 是否具备视觉能力（决定图片型 PDF 能否处理）
5. 能否派生并行子代理

同时探测工具矩阵并回显：`tar` / `bsdtar` / `unzip`、哈希命令、`textutil`、`pandoc`、`pdftotext`、PyMuPDF、python-docx。

据此定档，**档位你自己判定，不要抛给用户选**：

| 档位 | 条件 | 行为 |
| --- | --- | --- |
| 脚本档 | 能操作文件 + 有 Python | 走脚本，全格式，最快 |
| 手工档 | 能操作文件，无 Python | 流程一步不少，用系统命令逐步做，慢 |
| 纯对话档 | 不能读写 `{target}` | 只做分析出报告，**不动任何文件** |

纯对话档下第一句话就要说清「这次只出分析报告，不会动任何文件」，报告末尾附可复制的操作清单。

无 Python 且条目较多（约三十条以上）时，不要闷头开干，主动说一句：「装个 Python 会快很多，要我帮你装吗」。用户不装就明说会慢且可能中断，并靠断点续跑来做。**绝不擅自从网络下载并执行任何东西**，要装也先说清装什么、装到哪、怎么清理。

### 4. 建安全网

**唯一的安全保证是一份完整备份副本**，复制到 `{target}` 的同级 `<目录名>-备份-<时间戳>/`，或用户指定的持久路径。无条件执行，不允许因为「反正有 git」而跳过。用 `cp -R` 或等价能力即可。

git 只是可选的附加信息：碰巧检测到 `{target}` 在 git 仓库内且已被跟踪，就顺带告诉用户多一层保障；检测不到就不提。

回验前先断言备份仍存在，不存在则拒绝落盘。全部完成后提示备份位置，由用户决定何时删，**不自动清理**。

## 主流程六步

1. **清点与提取** —— 每个顶层条目产出一份文本 dump，外加**失败清单**与**可疑清单**。有 Python 时跑 `{skillDir}/scripts/extract_all.py --target {target}`
2. **分批评分与类型判定** —— 每条同时产出：类型、评分与逐条依据、分类、去重键。判据见 `references/scoring-and-taxonomy.md`
3. **全局去重仲裁** —— 独立一步，强制执行，不可与第 2 步合并。见 `references/dedup-arbitration.md`
4. **分类编号规划** —— dry-run 打印完整移动计划，交用户确认
5. **执行落盘与回验** —— 只移动不删除，落盘后与备份做全量内容指纹比对
6. **渲染报告与写账本** —— 报告由账本渲染而来，两者成对产出。模板见 `references/report-template.md`

能并行子代理时第 2 步分批派发，每批一份 JSON 由你合并；不能并行则串行分批，**每批处理完立刻把结果落盘再进下一批**。落盘是关键：串行时上下文持续累积，不落盘则后面的批次会因上下文挤压而降质，中断后也无法续跑。

**断点续跑是必备兜底。** 不少客户端对单轮对话的工具调用次数有限制，上百个条目会撞上去，表现为「跑到一半莫名停住」。每批落盘、账本记进度，用户说一句「继续」就能接上。

## 三态分流：不是 skill 的不许进主清单

评分之前先定类型，这是**硬路由**，不是报告里的一个描述列。

| 类型 | 去向 |
| --- | --- |
| skill | 主清单，参与编号与排序 |
| 参考素材 | `98-参考素材`，用 `M-` 编号，**不打分不排序** |
| 存疑 | 列出来问用户，不自行决定 |

正面特征（越多越像 skill）：含 `SKILL.md` 或带 name/description 的 frontmatter、有角色设定（「你是…」）、有面向执行者的流程步骤、规定了输出格式或交付物。

反面特征（命中任一即倾向参考素材）：

- **指令密度趋近于零**。第二人称指令词（你是 / 你需要 / 请）、流程词（步骤 / 第一步）、输出约定词（输出 / 交付 / 格式）都极少出现，通篇是陈述文体
- **正文以第三人称介绍「这个 skill 是什么」**。真 skill 用 frontmatter 承载元信息、正文直接下指令；正文里写着「Skill 名称: xxx / 作者: xxx」的是介绍页，不是 skill 本身
- **标题或首屏含自指词**：作业、展示、练习、分享、介绍、assignment
- **是填空模板、图解、汇报材料、观察报告、对话记录、设计稿**

PDF 和 pptx 天然偏向展示物料，判定时加重反面特征权重，但**不因格式直接定性**——确实有人把可用的 skill 导成 PDF。

有两类光看词频会判错，务必扫一眼正文开头：**某个 skill 的输出产物**（填好的行动卡、生成的报告，带着「上传给你的智能体」的说明，指令密度很高，但内容是某个人的具体问题，不可复用）和**纯理念介绍**（讲「为什么做这个技能」，作者自述口吻，第二人称指令为零）。两者都判参考素材，详见 `references/scoring-and-taxonomy.md`。

给一份写给人看的材料打分毫无意义，还会污染排序。参考素材与主清单允许双向流动，用户的调整决定写进账本，下次不再问。

## 去重：最容易出事的一步

核心判据只有一条，记牢：

> 只有「同一 skill 的不同版本」「同一份内容的不同导出格式」才算重复。**不同作者、不同方法论框架的同主题 skill，即使目标人群完全一样，也必须各自保留。**

分批打标记会同时产生两类错误，仲裁轮两类都要修：**过度合并**（一个键吞掉十几个独立条目，照此执行会误删）和**漏合并**（跨批次同一 skill 拿到不同键）。正反例与仲裁提示词模板见 `references/dedup-arbitration.md`。

## 三道校验关卡

流程接缝处最容易出事，每处一道硬校验，不过则停，不许带病往下走。

| 时机 | 校验内容 |
| --- | --- |
| 提取完成后 | dump 小于 500 字符、或条目内无 SKILL.md 且总提取量小于 1KB 的，进「可疑清单」强制人工过目 |
| 合并评分结果后 | 条目数等于清点数、分类值落在枚举内、分数在 0–100、无重复编号 |
| 报告生成后 | 报告每行的目标路径逐条断言存在于磁盘，编号在各分类内唯一 |

第一道尤其重要：提取「成功」但内容几乎为空的条目，在脚本层面是看不出来的。

## 报告与账本

报告默认命名 `Skill分析报告.md`，放 `{target}` 根下，用户可自定义。**不要叫 README.md**，使用者不一定是程序员。

账本 `Skill分析报告-数据.json` 与报告成对出现，用可见文件名（隐藏文件在访达里看不见，也容易被同步工具丢掉）。账本记录：整理时间、评分权重、使用的模型标识、分类枚举、报告实际文件名，以及每个条目的编号、**相对 `{target}` 的路径**、原始文件名、内容哈希、评分、类型、分类、**仲裁后的最终去重键**。

存相对路径是因为用户随时可能给目录改名——整理完成后主动问一次是否改名。

报告措辞按非程序员写：避免 frontmatter、references 这类术语；开头解释清楚评分怎么来、等级怎么分档、每列什么意思。

## 跨平台

流程与操作系统无关，差异在命令写法和文件名规则。有 Python 时脚本已屏蔽大部分差异，手工档下要按平台选：

- 哈希：按 `shasum` → `md5` → `md5sum` → `certutil -hashfile` 顺序探测取第一个可用。**不要假设 `md5sum` 存在**，macOS 上没有
- 解压：macOS 与 Win10 1803+ 自带 `tar`（即 bsdtar）；Linux 的 `bsdtar` 常需另装；Windows 另有 `Expand-Archive`
- 复制移动：Unix 是 `cp -R` / `mv`，Windows 是 `robocopy` / `move` 或 PowerShell 对应命令

**文件名一律按 Windows 最严规则清洗**：禁止 `< > : " / \ | ? *`，避开 `CON`、`PRN`、`NUL`、`COM1` 等保留名，路径总长控制在 260 字符内。非法字符换成全角等价物或短横线。这样生成的名字三个平台都安全。判断重名时**按小写比较**，因为 Linux 区分大小写而 macOS 与 Windows 不区分。

## 给使用者的体验要求

预设用户是把 skill 丢给智能体、说一句「帮我整理这个文件夹」，此外不想懂技术细节的人。

- **能力自检静默进行**，只在结论上说人话，不要抛出档位名称让用户选
- **开工前给规模预期**：多少条目、大概多久、会在哪两处停下来问他
- **交互确认点只有两处**（分类体系、重复项处理方式），每处都给默认选项，用户回一句「就按你说的」即可推进
- **中断能接上**，用户不需要理解机制，说「继续」就行

## 反模式

- 把「跑某个脚本」当成流程本身——没有 Python 就等于流程断了
- 因为有 git 就跳过备份
- 擅自从网络下载并执行二进制
- 分批评分时给各批次不同的评分锚点或分类枚举，导致口径漂移无法横向比较
- 用无引号的 `for` 循环批量解压——文件名含空格会被拆成多个参数而成批失败
- 把「可用性=否」写进报告却仍给它一个 skill 编号
- 增量整理时重排已有编号——编号是身份标识不是排序位
